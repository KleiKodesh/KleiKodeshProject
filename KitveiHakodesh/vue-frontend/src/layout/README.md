# layout

App shell components. Persistent chrome that wraps every page.

There is exactly one shell component; split view renders it twice. `src/App.vue` always renders pane 1 (`<AppShell :pane-id="1" />`) and renders pane 2 only while `bookViewStore.splitViewEnabled` is on, with a drag-handle divider between them. Split view requires a window at least `SPLIT_VIEW_MIN_WIDTH` (768px) wide and is disabled entirely in the VSTO/Word task-pane environment (`isVstoEnvironment`). Split/focus state (`splitViewEnabled`, `splitViewFraction`, `focusedPaneId`) lives in `bookViewStore`, not `tabStore`.

**AppShell.vue** — one shell instance = one pane. Takes `paneId?: 1 | 2` (default 1). Contains `<AppTitleBar :pane-id>` + `<AppPageView :pane-id>`. On setup as pane 2 it calls `tabStore.ensurePane2HasTab()` so pane 2 never renders empty. It `provide`s `paneId` and `PANE_NAVIGATION_KEY` so all descendants operate on the correct pane (see `usePaneNavigation` in `src/composables`). Any `pointerdown` inside the shell calls `bookViewStore.setFocusedPane(paneId)`. It is a **row**: `AppNavSidebar` (when `settingsStore.getNavSidebarVisible(paneId)`) owns the pane's edge for its full height, and `.app-shell-main` — the title bar above the content panel — sits beside it.

**AppTitleBar.vue** — 40px fixed header, one per pane. Left side, in order: hamburger menu, split-view toggle, theme toggle, toolbar toggle, PDF filter toggle — the split toggle sits next to the hamburger because both are window controls the rail takes over. Right side: home, new tab, close tab. **The hamburger, the split-view toggle and home are all dropped while this pane's `settingsStore.getNavSidebarVisible(paneId)` is on**: the rail is that same menu and carries all three itself, and a control is never offered in two places at once. The bar spans its pane's width, which starts where `AppNavSidebar` ends — it never spans across the rail. Center: active tab title and TOC path (interactive breadcrumb for book-view tabs), replaced by `AddressBar.vue` in search mode. It owns the markup and the two pieces of local UI state the template needs (`searchMode`, `navDropdownOpen`) — keyboard shortcuts are **not** here, see below.

**useSplitViewAvailable.ts** — whether the split-view toggle may be offered at all: never in the VSTO task pane, and not below `SPLIT_VIEW_MIN_WIDTH` (768). Read by `AppTitleBar` and `AppNavSidebar`, the two surfaces that offer the toggle, so they cannot disagree. `App.vue` imports the threshold but measures the app *element* rather than the window, because it is what auto-disables an open split when the element shrinks.

**useAppTitleBarShortcuts.ts** — every keyboard shortcut the title bar owns, installed once per pane. Add new shortcuts here, not in the component. Two groups, and picking the wrong one is the classic mistake: *pane-scoped* shortcuts (tab operations, book-view panels, navigation) fire only when that pane is focused, while *app-wide* ones (fullscreen, split view) are handled by pane 1 alone so they don't fire twice in split view. Also forwards `Ctrl`+key events out of child iframes (html/txt viewers) into the top-level keydown pipeline. Always match on `e.code`, never `e.key`. Update `ShortcutsReferenceList.vue` in the settings feature whenever a binding changes.

**AppPageView.vue** — fills remaining height, renders the active page via a route → async-component map. Picks the active tab from its `paneId` (`activeTabForPane(2)` vs `activeTab`). book-view, search, and txt-view are keyed by the active tab id and remount on tab switch. Adding a new route means registering it here.

**AddressBar.vue** — Explorer-style editable search field swapped into the title bar center on click (search mode). Reuses the global search engine and dropdown (`features/global-search/`: `useGlobalSearch`, `GlobalSearchDropdown`), the same pair behind the home page's search bar. The dropdown is open for the address bar's whole lifetime and lists `tabStore.recentLocations` — places the reader has been — whenever there are no search results (empty/short query, or a query that matched nothing), and the search results otherwise. It is **not** a tab list: nothing in it reflects which tabs are open, selecting a row navigates the current tab, and removing one closes nothing.

**Where the tab list lives.** Only the desktop host has one, and it is native: the FluentChromeTabs strip owns it, reached via `toggleChromeTabList()` in the bridge. `Ctrl+T` opens it; `Ctrl+Tab` / `Ctrl+Shift+Tab` open it as a hold-to-scroll switcher that stays up while `Ctrl` is held and activates the highlighted tab on release. That whole gesture is owned by C# (`TabListDropDown.BeginQuickSwitch`) — the popup takes OS focus as it opens, so the page never sees the matching keyup. Everywhere else (`!hasNativeChromeTabs`: VSTO task pane, dev browser) there is exactly **one tab** by construction — `tabStore.openTab` navigates in place instead of adding one, and `Ctrl+Tab` walks that tab's own back/forward history.

**AppTitleBarHistoryButton.vue** — one Back/Forward button (prop `direction: 'back' | 'forward'`, plus `paneId`), rendered twice in the title bar's `.bar-end`. A click steps one frame through the active tab's own history (`useAppShellPane.goBack/goForward`, also `Alt+ArrowRight` / `Alt+ArrowLeft`); press-and-hold (500ms, `onLongPress`) opens a teleported dropdown listing every frame in that direction, nearest first, and picking one jumps straight to it via `goToHistoryIndex`. Greyed out rather than hidden at the ends of the stack. Its visibility ids in `titleBarHiddenButtons` are the legacy `'prev-tab'` / `'next-tab'`.

**AppTitleBarNavDropdown.vue** — hamburger nav menu, anchored to the right edge of its button so it opens toward the screen center. Its destination rows come from `appNavItems.ts`, with the **workspaces row grouped among them above the divider** — like on the rail, it is about what you are working on, not about the window; below the divider come the settings row, the row that opens the nav sidebar, and (hosted only) pop-out — keyboard indexes for those are read off the `menuRows` list rather than counted by hand. The **workspaces row is not a destination**, despite where it sits: it opens `WorkspaceSubmenu` beside the menu instead of a tab, and stays held (`.nav-row--open`) while its panel is up. Because that panel is teleported, this menu's own outside-click watcher would otherwise read a click inside it as landing outside — hence the `ignore` on the submenu's exposed `panelEl`. Escape backs out one level at a time: the open submenu first, then the menu. **While the nav sidebar is up this menu is unreachable**: the title bar drops the hamburger and `Ctrl+M` is inert, because the sidebar is this same menu already on screen. So the sidebar row only ever *opens* it; the rail closes itself.

**appNavItems.ts** — the one list of nav destinations, in menu order: `APP_NAV_ITEMS` plus `APP_NAV_SETTINGS_ITEM` (which sits below a divider in both surfaces). Read by `AppTitleBarNavDropdown.vue` and `AppNavSidebar.vue` so the two can never drift. The label is the routing key — `useAppNavigation` maps it to a route.

**appNavUpdateItem.ts** — the update row's face for every nav surface (Windows / Firefox / Chrome hybrid): `useAppNavUpdateItem()` returns `item` (null while nothing is downloading, ready or installing) with the text, tooltip, icon, colour and `disabled`, plus `install`. Read by `AppTitleBarNavDropdown.vue` (first row after the divider, coloured start edge), `AppNavSidebar.vue` (first button of the controls group; the more button wears its dot while it is folded away), `AppNavSidebarOverflowMenu.vue` and the hamburger in `AppTitleBar.vue` (a dot in the update's colour, tooltip gains the row text). Colour ages like Chrome's menu tint: accent → orange after 2 days → red after 7 (`composables/useUpdateNavState.ts`). No dismissal — the row stays until clicked. Replaced the bottom-corner `UpdateAvailablePrompt` (2026-10-28).

**WorkspaceMenu.vue** — workspace management (switch, create, rename, delete) as a menu panel. It was a page (`/workspaces`, a home tile, `Ctrl+9`) and is deliberately not one any more: the list is a few short rows picked from mid-task, so it is a **picker, not a destination**. There is no route, no tile and no quick-nav digit — reaching it is the shell's job, which is why it lives here rather than under `features/`. It paints no surface of its own; the host panel does, so it drops into either surface unchanged. Every mutation is `workspaceStore`'s; what is here is the rows and three bits of row-local state (which row is renaming, which is confirming a delete, the new-name box). Switching or deleting the active workspace ends in `window.location.reload()`. **The whole menu is one keyboard list, create box included.** The rows and the new-name box are stops on a single up/down walk (`focusedIndex === workspaces.length` *is* the box), so arrowing past the last row puts the caret in the box and arrowing up out of it returns to the last row — no tab stop to hunt for, because creating a workspace is the same job as picking one. Moving onto the box focuses it for real and moving off hands focus back to the host panel, or the caret would stay behind and every further arrow would walk the text instead of the list. On a row: **Enter** switches, **Delete** starts the delete confirmation (carrying the delete *button's* guard — the last workspace cannot go), **F2** starts a rename (the Windows rename key, and otherwise the rename button is pointer-only). In the box: **Enter** creates. **Home/End** jump to the ends of the walk but are surrendered to the caret while the box has it, where they mean start/end of the text. **A row asking "delete this?" owns both answer keys for as long as the question stands: Enter deletes, Escape backs out.** Neither reaches its usual meaning (switch to this workspace; close the panel) until the question is gone — a confirmation the reader cannot answer from the keyboard they raised it with is not much of one. Activation is otherwise **ignored on a row that is renaming**, where Enter already means "save the name". The highlight **starts on the active workspace** rather than at the top, and is recomputed off **list membership, not `activeId`** — deleting a non-active workspace leaves `activeId` untouched while every index below the deleted row shifts up, which would otherwise leave the highlight on the wrong row or past the end. It does **not** use `useListKeys`, though the rows keep that contract's `data-nav-item` marker and `is-focused` class so they look like every other list in the app: that composable binds to the container it is given and assumes the container holds the focus, which this menu never does — see `WorkspaceSubmenu` above for why the keys are bound on the panel instead. Leaving the rename box **hands the focus back to the panel** on `nextTick` (the box is still mounted on the current tick, so focusing the panel earlier just lets the box take it straight back) — without it the reader finishes a rename and finds the arrows dead, the focus stranded on a removed element. Starting a rename or a delete-confirm also **pins the walk to that row**, so cancelling returns the reader where they were rather than to nothing, and clicking a row's rename button makes it the keyboard's row too. What remains at this root is a narrow guard: while the caret is in the rename or create box, only the typing is stopped from reaching the panel. Escape is deliberately let through — it is the host's "back out one level".

**WorkspaceSubmenu.vue** — `WorkspaceMenu` as a real submenu, flying out sideways from whatever row or button opened it. Both surfaces render **this**, so the anchoring, the viewport clamping and the dismissal are written once; callers own only `v-model:open`, `anchor`, `keepClearOf`, and `prefer` (which physical side to try first — RTL, so both currently pass `'left'`, opening inward off the window's right edge). It is `<Teleport>`ed to the body with `position: fixed` because the rail and the dropdown are both scroll boxes that would clip a panel positioned inside them — and because fixed-to-the-viewport is what makes clamping possible.

`place()` measures, then places. It flips to the other side of the anchor when the preferred side has no room, gives up the flip when neither side fits and sits against the roomier edge, and takes a `max-height` from the vertical space actually left, so the panel **never leaves the viewport at any window size** — which matters most in the VSTO task pane. **It also never covers the surface it came from**: each caller passes `keepClearOf` (the rail's own sheet, the dropdown's root) and the band the panel may occupy is cut back to one side of it — the side the anchor is on, less a `KEEP_CLEAR_GAP`. That gap is deliberately larger than the anchor gap: it separates two floating sheets that each carry a frame and a shadow, and touching frames read as one wider panel with a seam down it. It holds at every window width, including the narrow ones where the panel shrinks. In a window too narrow for both, the panel gives up its *own width* (a `max-width`; the menu inside carries `min-width: 0` so it can follow) rather than the ground it was told to keep clear, so the rail stays fully visible and the panel scrolls inside what's left.

Both caps come off before measuring and go back on after, written **imperatively on the element, never through a ref** — a ref reaches the DOM on Vue's next flush, i.e. *after* `place()`'s own measurements, which made the clamp sticky downward: it could only ever shrink across re-places and never recovered room a resize gave back. (`scrollHeight` cannot substitute to save the reflow: the panel is `overflow: hidden` and the inner `.ws-list` is what scrolls, so the panel never overflows and its `scrollHeight` is just its clamped height again.) Order matters: the width cap is applied *before* the height is measured, and the height is re-read *after* it, since narrowing rewraps the rows. It re-places on resize, on capture-phase scroll, and on its own `ResizeObserver`, since rows appearing or swapping for a rename box changes its height — clearing and restoring within one synchronous pass is what keeps that observer from re-entering, as a pass landing on the caps already in force ends the frame at the size it started. **That symmetry is an invariant: an `await` between the clear and the restore would split them across frames and bring the loop back, so `place()` stays synchronous.** A **scroll** additionally checks whether the anchor is still visible inside its `keepClearOf` surface, and **closes instead of following** when it isn't — the dropdown is itself a scroll box with a `max-height`, so a row can scroll out from under an open panel, which would otherwise hang there beside a row nobody can see. A **resize** only ever re-places: the anchor is still the row the reader picked, a shrinking window is precisely when the clamping earns its keep, and closing there would yank the panel away mid-drag. It is hidden for its first frame (`placed`) because placement needs a measurement first. **It opens on click only** — never on hover. It used to open on hover, as a submenu conventionally does, which put a panel over the page every time the pointer merely crossed the button on its way somewhere else and made it the one control in the bar that acted before it was asked; the two hover timers (intent delay, close grace) and the `pointerType: 'touch'` guard that arrangement needed are all gone with it. **The keyboard route is `F8`** (`useAppTitleBarShortcuts`, threaded in as `toggleWorkspaces`), which is what lets the button stay click-only without becoming harder to reach. A bare function key rather than a Ctrl pair, because every free Ctrl+letter is one the *browser* claims before the page ever sees it — `Ctrl+Shift+W` closes the window outright and `preventDefault` cannot call that back, which is how it was first written and why it had to change. F8 has no Chromium binding and joins the F-key family this app already has (F1 settings, F9 reading mode, F11 fullscreen). Escape closes the panel from anywhere inside, and **this panel is also where the menu's list keys are bound**, though the list lives in `WorkspaceMenu`. It has to be: the panel takes the focus on open, so it is the keydown target, and events bubble *up* from a target rather than down into its children — a listener on the menu, which is this panel's child, is never on the path and never fires. (That is exactly how the arrow keys first shipped dead, bound below the focus with `useListKeys`.) So the panel takes every keydown, offers it to the menu's exposed `onPanelKeydown`, and consumes it only when the menu reports it used it. The one case that routes itself is the caret sitting in one of the menu's text fields: the field is then the target and the keydown passes through the panel on its way up, which is what lets the walk keep working from inside the create box — so those fields stop only their own typing and let the walk's keys (arrows, Home/End, Enter, Escape) through, a blanket `stopPropagation` there having severed the create box from the walk entirely. **Escape is offered to the menu first, not handled here**: a row mid-rename or mid-delete-confirm is a level of the menu's own, and Escape must back out of that before it backs out of the panel — taking it here first shut the whole picker on a cancelled rename. The menu returns false once it has no level left, and only then does Escape close. **The focus call also clears `visibility` straight on the element first**, and that is load-bearing rather than defensive: `place()` ends by setting the `placed` ref, which reaches the DOM only on Vue's next flush, so at the moment `.focus()` runs the panel is still `visibility: hidden` from its first frame — and a hidden element cannot take focus. The call was silently ignored, focus stayed on `<body>`, and every one of the panel's keys went nowhere. It is the same ref-versus-element timing trap `place()` already documents for its own max-height writes. For both to work the panel **takes the focus when it opens** — `tabindex="-1"` only makes it focusable, and without the explicit `.focus()` the focus stays on a button in a different DOM tree, where a keydown never passes through the teleported panel at all. That focus call is **unconditional**, which it could not be while hover could open the panel: an open nobody asked for must not pull the caret out of whatever the reader was typing in, but every open is deliberate now. The dropdown takes the focus back on close, since its arrow-key navigation is bound to its own root. Callers call the exposed `toggle()` rather than flipping `open` themselves, so pointer and keyboard go through one door — and with hover gone it is a plain flip again: the only thing that can have opened the panel before a click is an earlier click or the shortcut, and for both a second press meaning "close" is right. (It was deliberately *not* a flip while hover existed, because the pointer is by definition hovering the row it clicks, so hover had already opened the panel and a true toggle shut it in the user's face — that hazard left with the hover.) Dismissal is click-away, a second press, or Escape. It needs no reopen guard, unlike the other `useDropdownClose` callers: those pass a wrapper that *contains* their toggle button, so a click on it never reaches the composable's toggle-button branch, whereas here the panel is teleported and the anchor lives in another tree, making that branch the normal path — and on it the composable deliberately does **not** close, leaving the job to `toggle()`. It also exposes `panelEl`: a host with its own outside-click watcher (the dropdown) must add the teleported element to its `ignore`, or typing in the panel closes the menu underneath it; `$el` can't serve, since the component's root is a Teleport.

**AppNavSidebar.vue** — the nav menu as an always-on icon rail down the side of the pane, one per pane, rendered by `AppShell` while that pane's `settingsStore.getNavSidebarVisible(paneId)` is on. **State is per pane and persisted per pane**: pane 1 under `app.navSidebar`, pane 2 under `app.navSidebar.pane2`. The **default** is host-dependent — on in the standalone demo app, off in the VSTO task pane (too narrow to give 44px away) and in the dev browser, which mirrors the task pane. It keys off `hasNativeChromeTabs`, which is already exactly that distinction (has the bridge, is not VSTO), rather than a second flag meaning the same thing. A default only: once the reader has toggled a rail, that pane's stored value wins. The panes never mirror each other — opening or closing one rail leaves the other alone, and each remembers its own answer across a restart, like every other per-pane value. Read and write it through `getNavSidebarVisible(paneId)` / `setNavSidebarVisible(paneId, value)`; there is no single global flag to reach for. **It defines an area to itself.** The rail owns the pane's edge for the pane's full height, and everything belonging to the document starts beside it — the title bar included, since that is the tab's title, breadcrumb and per-tab controls, i.e. this app's tab-header strip. The rail is a sibling of the *shell that contains* that strip, never of the strip itself, so nothing ever spans across the rail. It splits with the pane — each pane gets its own, because a pane here is a whole shell (own title bar, own tabs, own history), not an editor group. **It is a docked sheet, not the frame** — `--bg-secondary` on a 1px `--border-color` frame with 6px rounded corners, the same surface and frame as the `AppTitleBarNavDropdown` that offers the same items, so it reads as that menu docked rather than as the app's frame thickened down one side. It fills its 44px strip and is inset 6px at the top and bottom only, which is all the corners need to read; the side against the pane's edge has **no border and square corners**, so the sheet runs straight off that edge, and the frame and the two rounded corners face the page. No shadow: in this app only floating panels cast one (see `CommentaryPanelHost`), docked surfaces never do. 44px wide with **32×32** items — the 24px glyph plus an even 4px inset, which is where the reference's hover background actually lands — a 6px gutter each side, 6px between them, and the app's 4px radius. Size the item from the hover band, not from the icon pitch: reading the pitch as the item size made every target 12px too big. One flat column on a uniform 38px pitch: home and the destinations at the top, then a flex spacer (`.nav-spacer`, space rather than a rule), then the rail's own controls — the split-view toggle, pop-out, settings and the collapse button, spaced like everything above them because the overflow arithmetic counts every child on that one pitch. The split-view toggle **moves in here** while the rail is up (`AppTitleBar` drops it, as it drops the hamburger) so a window control is never offered in two places at once; it still honours the same `titleBarHiddenButtons` entry, `'split-view'`. Icons only, each with its label as the tooltip; a double-chevron button at the bottom of the rail closes it again — `ChevronDoubleRight`, pointing at the edge it folds back into, and `ChevronDoubleLeft` on the menu row that opens it (RTL, so the rail is on the right). Navigation goes through `useAppNavigation`, so a rail opens its destination in its own pane's tabs. The workspaces button is **not** in `APP_NAV_ITEMS` either, and for a stronger reason than home: it is not a destination at all — there is no page and no route, so it opens `WorkspaceSubmenu` beside the rail (`prefer="left"`, inward off the docked edge) and stays held (`.nav-btn--on`) while that panel is up. It sits with the destinations rather than with the controls below the spacer because it is about what you are working on, not about the rail or the window. Home is **not** in `APP_NAV_ITEMS` and is rendered separately: that list is destinations opened in a new tab by label, whereas `goHome()` reuses the pane's existing home tab instead of stacking another — the same reason the title bar renders its own home button rather than driving one from that list. The title bar's copy is the one that hides while the rail is up; between them home is always offered by exactly one button (a count of buttons, not of tabs — a new-tab gesture stacks home tabs freely; only `goHome()` consolidates). **In a pane too short for every button, the tail of the column collapses into a "more" button** rather than scrolling away invisibly (the rail's scrollbar is hidden). The rail is one flat ordered list — home, the destinations, workspaces, split view, pop-out, settings — and whatever the height cuts off, from the bottom up, moves into the flyout in that same order (so the rail's own controls go first, the destinations last). **The one button that never collapses is the hide button**, which keeps the rail's floor with the "more" button directly above it: it is the only way to close the rail (the menu row that opened it is gone while it is up), so a rail short enough to fold it away would be a rail nobody could close. It has no key in the overflow list at all — only a reserved slot. The fit lives in `useAppNavSidebarOverflow.ts`: it measures the panel's content height (`useElementSize`) and computes from two constants mirroring the rail's CSS — the 32px button and the 6px gap — so nothing has to render before it can be counted. The one-line arithmetic (n buttons need n×38) relies on every child sharing that pitch, the spacer included, which costs one extra flex gap even at zero height. Conditional buttons (split view, pop-out) are simply absent from the key list when unavailable; destinations and settings are keyed by their labels (the label IS the routing key), the non-destinations by names of their own (`home`, `workspaces`, `split-view`, `pop-out`). The "more" button and the pinned hide button take the last two slots, so it holds `.nav-btn--on` while its flyout is up, and unmounts the moment a resize gives the room back — watchers close the flyout with it, and close the rail's workspace picker when the workspaces button collapses out from under it. The rail keeps every collapsed row's **action**: the flyout emits `select` with the key and `onOverflowRowSelect` dispatches (home → `goHome`, split view → toggle, pop-out, anything else → `navigateInNewTab` by label).

**useAppNavSidebarOverflow.ts** — that fit arithmetic: takes the panel element ref and the split-button visibility, returns `hasNavOverflow`, `railButtonVisible(key)`, `visibleNavItems` (always a prefix of `APP_NAV_ITEMS`) and `overflowedRailKeys` (the collapsed tail, rail order). The 32/6 constants live here; change the CSS, change them.

**AppNavSidebarOverflowMenu.vue** — the flyout: the collapsed tail as labelled rows (icon, label, shortcut — the hamburger menu's rows, relocated), built from the `collapsedKeys` prop. The rail owns what each row does (`select`); this menu owns each key's face, read off the same tables the rail's buttons read — the split-view row's label and icon follow `bookViewStore.splitViewEnabled` just as the rail button's do. The **workspaces row is the one with behaviour of its own**: not an action but a submenu row, opening `WorkspaceSubmenu` beside this menu (`keepClearOf` the menu itself, `prefer="left"`), held with `.menu-row--open` while up, its element picked out of the `v-for` by a function ref, its teleported panel added to this menu's `useDropdownClose` `ignore` (else typing in the picker closes the menu under it — same as the hamburger menu). Escape backs out one level at a time: the open picker first, then the menu. Teleported to the body with `position: fixed`, `useDropdownClose` with the more button as `toggleButton`, and the panel takes focus on open so Escape has somewhere to land (always safe — it only ever opens by click). Deliberately simpler placement than `WorkspaceSubmenu`: one host and one possible side — the rail is docked to the window's physical right edge, so it always opens inward (left), never over the sheet passed as `keepClearOf`. What remains is the vertical work, its whole reason to exist (it only opens in short windows): top-aligned to its button, lifted until it fits, capped to the viewport and scrolling inside when even that is not enough. The cap comes off before measuring and goes back after, written straight on the element (a ref reaches the DOM after the reads — see `WorkspaceSubmenu`), and it re-places on window resize and whenever `collapsedKeys` changes while open, since a shrink feeds it more rows.

**AppTitleBarTocBreadcrumb.vue** — renders the interactive TOC breadcrumb in the title bar center for `/book-view` tabs. Each segment label is shown as text; between non-last segments a chevron button opens `AppTitleBarBreadcrumbChevronDropdown` listing sibling entries. Receives `segments` from `useAppTitleBarTocBreadcrumb` and emits `navigate-to-entry`.

**AppTitleBarBreadcrumbChevronDropdown.vue** — teleported chevron dropdown that lists TOC sibling entries. Uses `useDropdownClose`, `<Teleport to="body">`, and `position: fixed` coordinates from `getBoundingClientRect`. Emits `select` with the chosen `TocEntry`.

**useAppTitleBarTocBreadcrumb.ts** — parses `tab.tocPath` (a `" · "`-separated string) into `TocBreadcrumbSegment[]`. Reads `TocEntry[]` from the `TocBridge` registered in `bookViewStore` — never queries the database directly. Returns an empty array for non-book-view tabs or when no bridge is registered yet.
